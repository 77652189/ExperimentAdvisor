# ADR-0015：贝叶斯优化补上模型校验（留一法 Q²）和叙述性解读

## 元数据

- 决策发生时间：2026-08-12（本次会话）
- 本记录补记时间：2026-08-12

## 背景

ADR-0014 给响应面(CCD)补了四项深入分析后，两条并行分析路线（ADR-0009）明显不对称：CCD 有 R²、失拟检验、每项系数显著性、外加置信区间/灵敏度/鞍点判别/联合优化；`recommend_round2_bo_batch` 拟合的两个 GP（产量、OD600）除了 `predicted_yield_std` 外，没有任何"这个模型该不该信"的诊断——`predicted_yield_std` 算出来了、也显示在推荐表里，但排序和过滤只看预测均值+OD600硬阈值，这个不确定度不参与任何决策，纯粹是摆在那里。同时 BO 推荐表生成完就结束了，没有类似 CCD 那套"这批数据在说什么、下一步怎么办"的解读。

用户在审视这个不对称后，选择先补两块：GP 的校验指标、BO 推荐的叙述性解读（CCD vs BO 两条路线互相对照暂不做，留待以后）。

## 决策

1. **留一法交叉验证走显式重新拟合，不用解析捷径**：`gp_leave_one_out_cv` 对每个样本逐个拿掉、用剩下的重新拟合 GP、预测被拿掉的点，重复 n 次——不是精确 GP 回归本身存在的解析 LOO 公式（通过精度矩阵直接算，不用重新拟合）。这批数据 n 很小（round 1 单独 ~16-20 行，合并 round 2 后最多几十行），n 次重新拟合的耗时完全可接受，而"重新拟合再预测一个点"比"伸进 gpytorch 内部拿精度矩阵算解析式"更容易肉眼核对对不对——和 `recommend_round2_bo_batch` 自己放弃联合约束采集函数、改用"两个GP+硬过滤+排序"的取舍是同一个理由（这个数据量下，好核对比精巧更重要）。
2. **指标是 Q²，不是 R²**：`1 - SS_留一法残差/SS_总变差`，DOE/QSAR 领域衡量"模型对没见过的新点预测得怎么样"的标准指标，和 R² 衡量"模型对训练点本身拟合得怎么样"是不同的问题。`recommend_round2_bo_batch` 的 GP 结构上没有 R²（也不该硬凑一个），Q² 是这两个 GP 唯一的"能不能信"的量化答案。
3. **交叉验证是按钮触发，不自动跑**：n 次重新拟合比单次拟合贵 n 倍，不能在每次生成推荐、每次页面重跑时都自动算——放进独立的折叠框+按钮，用户主动点了才算，算完存 `session_state`，直到下次显式重新点击前都复用。
4. **叙述性解读（`summarize_bo_recommendation`）覆盖三件独立的事，CV 相关的部分是可选输入**：① Q² 分档解读（未提供 CV 结果时完全跳过，不假装有答案）；② OD600 可行候选占比是否过窄（始终有，不需要 CV）；③ 排名第一的推荐点相对不确定度大不大，直接把之前"只是显示、不参与决策"的 `predicted_yield_std` 用在解读上——不确定度大就是「偏探索」，小就是「偏利用」，这是让这个数字第一次真正说上话。CCD vs BO 的一致性对照本轮不做（用户没选这个方向），未来若要做应该作为这个函数的第四类独立解读，而不是塞进已有的三类里。
5. **两个 BO 入口（仅 Round1 / 合并 Round1+Round2）共用同一段渲染代码**：`_pichia_render_bo_recommendation_section` 把推荐表、GP 偏依赖图、叙述解读、交叉验证折叠框合并成一个函数，两个入口都调用它、只传入各自的训练数据和 session_state key。这两处渲染代码原本就是逐字重复的，新增内容如果继续各写一遍，两处早晚会在格式上悄悄跑偏。

## 后果

- `gp_leave_one_out_cv`/`summarize_bo_recommendation` 都是纯函数，不感知 Streamlit；`round2_design.py` 继续不含变量名到中文标签的翻译表，`summarize_bo_recommendation` 的解读文本本身直接写中文（和 `summarize_response_surface` 一致的既有约定：叙述文本本身用中文，只有变量名占位符留给 UI 层替换——这里"产量"/"OD600"是两个固定的目标指标，不是动态变量名，直接硬写中文，不新增翻译表）。
- 交叉验证结果按 `{"yield": ..., "od": ...}` 存成一份 dict，两个 BO 入口各自独立的 `session_state` key（`round2_bo_cv_result` / `round2_combined_bo_cv_result`），互不覆盖；和推荐结果本身一样，重新生成推荐批次不会自动清掉上一次的交叉验证结果，需要用户自己注意两者是否还对应同一批数据。
- 用真实 Y103 数据验证时，两条 BO 路线的 Q² 结果并不好看（仅 round 1 的产量模型 Q²≈0.13，合并数据后 OD600 模型 Q²≈0.28）——这不是 bug，是如实反映当前数据量下这两个 GP 的预测能力确实有限，叙述解读会据实给出"打折看"的提示，而不是回避这个不好看的数字。

## 验证

- `tests/test_round2_design.py` 新增 8 条：`gp_leave_one_out_cv` 的最小样本量报错、返回数组形状/一致性（`residuals == actual - predicted`）、可学习信号 vs 纯噪声信号的 Q² 对比（可学习信号 Q²>0.5 且明显高于纯噪声）；`summarize_bo_recommendation` 按分支覆盖 Q² 三档、可行占比过窄告警、探索/利用两种不确定度读法、产量和 OD600 两个模型独立解读互不干扰。
- `App/pages_pichia.py` 侧用真实 Y103 数据端到端跑通（AppTest 脚本，未提交仓库）：两个 BO 入口都能生成推荐、点击"运行交叉验证"后正确显示 Q²/RMSE 指标和留一法残差图，且叙述解读的三个严重级别（success/info/warning）在真实数据下都被触发到过；确认过程中未产生任何异常，也没有污染 `data/pichia/final/` 里的真实数据文件。
